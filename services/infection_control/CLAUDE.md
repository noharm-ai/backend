# Infection Control Rule

- Services: `services/infection_control/infection_control_status_service.py` (the rule) and `services/infection_control/antimicrobial_timeline_service.py` (how prescriptions are grouped into courses)
- Decides when an admission is followed, which pending reasons open or resolve, when evaluations close, and the PENDING / REVISED / CLOSED status
- **Exam triggers.** Besides its optional triggers (`gatilhos`: expiry, posology change), an evaluation may turn on the schema's exam trigger rules (the review sends their ids in `examTriggers`; an id of a rule deleted meanwhile is left out). The users define the rules (`GET`/`PUT /infection-control/exam-triggers`, the PUT replacing the list, `WRITE_INFECTION_CONTROL`), kept in the schema's `memoria` (kind `infection-control-exam-triggers`, one record holding the list; a schema with no record gets a copy of the global rules in `public.memoria`, same kind, the first time they are read or saved, and edits its own from then on; an empty list is a schema that removed them all, not copied again; an admin kind, so the generic `/memory` endpoints can't write it). Model `models/infection_control_config.py`: `id` (given by the backend, kept on edit), `name`, `examRef` from the fixed catalog `EXAM_TRIGGER_EXAMS` (`pcru`, `temp`, `ckd`, `ckd21`, `h_conleuc`, `procalcitonina_adult`, `van`: references, `segmentoexame.tpexame_ref`, every active exam mapped to one counts, the latest result among them winning, as in the prescription view), the conditions (`value*` and `variation*`, each with `Above` >, `AtLeast` >=, `Below` <, `AtMost` <=; the variation from the baseline in signed percent; all set must hold on one result; at least one), `fromCourseDay` (results from that treatment day of the course on, D1 the first 24 hours: `4` is after D3) and `enabledByDefault` (on in a new evaluation). `ckd` and `ckd21` are not results of their own: they are calculated from the creatinine (the schema's exam with abbreviation `creatinina`, as the exams screen finds it) with the patient's data, adults only. The GET also lists the catalog; a rule or an exam is `available` when the schema has results for it (otherwise it would never fire: the form shows it disabled with a warning; the review save doesn't check it). Each rule turned on is copied on the evaluation with its baseline, among its triggers: `ci_avaliacao_atm.gatilhos` keeps the pending types as ints and every trigger with parameters as an object with a `type` (`exam`), so a new kind of trigger needs no new column; read them with `evaluation_triggers.pending_triggers` (re-exported by `infection_control_status_service`, kept apart so the trigger services can import it) and `exam_trigger_service.evaluation_exam_triggers`, never the raw list. The one exception is outside this repository: the exams cache job of `backend-private` queues only the admissions with an active evaluation (`tp_status` 1) whose `gatilhos` holds an exam trigger on the exam of the new result (`gatilhos @> [{"type": "exam", "examRef": <reference>}]`, the reference mapped from `segmentoexame` as `exam_sources` does), so that format (ints and objects with `type` and, for an exam trigger, `examRef` in lower case; `TRIGGER_TYPE_EXAM`, `AntimicrobialEvaluationStatusEnum.ACTIVE`) is a contract shared with it: change it in both repositories, with `tests/test_exams_cache_db.py` there. The baseline is the latest result of the exam when the review is saved (the `exame` table, or the DynamoDB archive when it has none), so editing or deleting a rule never changes what an evaluation watches. While the evaluation is in force, a result dated after the baseline (or after the evaluation without one) that meets a rule opens a reason of the drug (`EXAM_RESULT`, one per evaluation naming every rule met in `detalhes.matches`), settled by a new evaluation; a variation is not met without a baseline, and from a zero baseline any rise is unbounded (a rise condition is met, a fall is not; the match keeps no variation). The rule reads the results only from the exams cache (Redis `{schema}:{id_patient}:exames`, read in `exam_trigger_service`, the same prescalc reads), so `sync_admission`/`apply_rule` take the schema. The cache keeps the latest result of each exam and is filled every ~30 minutes by the exams cache job of `backend-private` (only schemas with more than ~1000 `exame` rows), which then queues the patient's followed admissions with an active evaluation watching an exam trigger on that exam for the light run (reason `exams_cache`): a result the cache replaced before the rule ran is not seen. Tests fake the cache (`cache_service.get_hgetall`). Service `services/infection_control/exam_trigger_service.py`. Tests: `tests/unit/test_infection_control_exam_triggers.py` and `tests/integration/infection_control/test_exam_triggers.py`
- **Culture trigger.** An optional trigger of each drug evaluation, like expiry and posology (the pending type `CULTURE_RESULT`, 8, kept in `gatilhos` as an int; the review form turns it on by default; every schema has its cultures in DynamoDB, so it checks no feature): while the evaluation is in force, a culture result of the patient that reached the culture summary after the evaluation was made opens a reason of the drug (`CULTURE_RESULT`, one per evaluation, `detalhes` with the latest `releaseDate` and the new `cultures`, one per material and microorganism, newest release first, at most 10), settled by a new evaluation. While it stays open, each run refreshes its `detalhes`, so a culture that comes after it is listed too. Any culture with an antibiogram row counts, whatever drug it tests: the summary holds only those (a culture released without a drug row, e.g. a negative one or one whose antibiogram is pending, is not there). The rule reads the cultures only from the DynamoDB culture summary (`noharm_cultura_resumo`, `culture_service.get_culture_summary`), and only in the scheduled job (origin `JOB`: a review save holds the record while it runs, and the next run sees what it would), once per run and only when an evaluation in force watches them, with the reading of the protocol variable `cultureReleaseTime` (`culture_service.released_items`: an active item with a lab result; a prediction or a pending collection is not one). A result counts by when it reached the summary (`resultArrival`, from the item's `resultado_em`, written in UTC by the culture cache job of `backend-private` when it first writes that result), not by the lab's release, which can come long before (the job runs every 5 minutes, the integration may be late); an item written before `resultado_em` existed falls back to its release date. Dates with an offset are read in local time (`culture_service.parse_local_datetime`). A failure to read the summary reads as no culture and never resolves an open reason. That job queues the patient's followed admissions with an active evaluation whose `gatilhos` holds `8` (`gatilhos @> [8]`) for the light run (reason `culture_cache`) when it writes a new result: that value and `resultado_em` are a contract shared with it, with `tests/test_cultura_cache_queue_db.py` and `tests/test_cultura_cache_service.py` there. Service `services/infection_control/culture_trigger_service.py`. Tests: `tests/unit/test_infection_control_culture_trigger.py` and `tests/integration/infection_control/test_culture_trigger.py`
- Each drug evaluated in a review tells why it is given (`ci_avaliacao_atm.tp_tratamento`, `AntimicrobialTreatmentTypeEnum`: empirical, culture guided, surgical or medical prophylaxis) and the infection foci (`tp_focos_infeccao`, an array of `InfectionFocusEnum`: one or more), required by the review save; only a prophylaxis may leave the foci empty. Evaluations made before they were asked have both empty. The frontend keeps the same codes (`models/InfectionControlEnum.ts`) and their labels
- **The rule lives only in this repository.** The review save, the manual follow, the backfill and the scheduled job all run it.
- Each run also stores on `ci_atendimento.indicadores` what it saw running (`admission_features`: each running course with its drug, substance, AWaRe level and start, plus `evaluatedPosology` when its evaluation watches posology changes and no posology reason of the drug is open, and whether a non-conformity is in force). The worklist filters read it instead of joining prescriptions (`antimicrobials`: a list of criteria, each met by a running course of its own, so the drug or substance and the treatment day of a criterion go together and several can be asked at once, e.g. amoxicillin on D1 and vancomycin on D2; AWaRe is a separate filter), as the prescription prioritization reads `prescricao.indicadores`. Prescalc doesn't fill it: an admission it starts following shows up in those filters after the next job run.
- **The scheduled job is split between two repositories.** `backend-private` (`lambda_infection_control.py`) only schedules it: it lists the followed admissions of each schema with the feature on and calls `static.infection_control_sync` here synchronously, one admission at a time, so a single backend invocation (and database session) runs at once. The entry (`services/infection_control/infection_control_job_service.py`) applies the rule to that admission and answers `processed`, `changed` or `skipped` (a record held by a review save is skipped after a short lock timeout).
- Keep the contract (`schema`/`admission_number` in; `processed`/`changed`/`skipped` out) in step with `services/infection_control_service.py` in `backend-private`
- **Light run and its queue.** Between the full runs (every followed admission, a few times a day), a light run applies the rule only to the admissions queued for it, with the same entry. It is the infection control consumer of the admission queues (see `docs/agents/admission-queues.md`): the exams cache job of `backend-private` queues the admissions with an active evaluation watching an exam trigger on an exam whose cached result changed (see Exam triggers above), its cultura cache job the ones with an active evaluation watching cultures when the patient has a new released culture result (see Culture trigger above), and prescalc queues an admission followed after its hook (pending or revised) only when an antimicrobial it processed (not suspended) can open a reason, decided in Python by `infection_control_status_service.prescalc_needs_rule` from the record's `indicadores` (one read, only when the prescription has antimicrobials; none otherwise): the drug is not among the running courses (a new drug or a restart; a record prescalc just created has no courses and one it reopened has none, so these are always queued), or its course keeps `evaluatedPosology` (stored by the rule when the evaluation watches posology changes and no posology reason of the drug is open) and none of the drug's items is prescribed as evaluated (`same_posology`, on the drug list fields mapped by `drug_list_posology`). A course kept before `evaluatedPosology` existed doesn't trigger it until the rule runs on it again. A daily prescription repeating a running antimicrobial as evaluated, a CPOE re-run of the day or a prescription without antimicrobials queues nothing. The job entry reads when it was queued before the rule and dequeues after it. A record held by a writer (`skipped` on the lock) stays queued; an admission not followed is dequeued. What only time changes (an evaluation expiring, a course ending, a discharge), a posology change of a course whose evaluation doesn't watch it, a new prescription-day (`fkprescricao_ultima`, whose department, bed and segment the worklist shows) and what doesn't go through prescalc (suspensions) are left to the full run. Tests: `tests/integration/infection_control/test_queue.py`
- **Report summary.** Each run also keeps `ci_atendimento.resumo_acompanhamento` (`services/infection_control/infection_control_summary_service.py`): every antimicrobial course as the timeline groups it (a running one at day precision, `coveredUntil`), and the department of each day. It is written only when it changes, since the job runs several times a day, and the model column is `deferred()`. The infection control report (`reports/InfectionControlReport.py` in `long-running-tasks`) builds its files from it with SQL alone, so the course grouping never leaves this repository: change the summary's contract (`v`, documented in the service's docstring) together with that report. Closed admissions without a summary are filled by `POST /infection-control/backfill-summary`
- Tests: `tests/unit/test_infection_control_status_rule.py` and `tests/integration/infection_control/` (the job entry in `test_job.py`, the summary in `test_summary.py`)
